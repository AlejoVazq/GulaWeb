# Fase 8 — Reportes: Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Reportes del local para dueño y encargado: períodos semana / mes / trimestre / semestre / año / personalizado; ventas totales y por método, egresos, resultado, ticket promedio, productos más vendidos, ventas por mesero, por origen y por franja horaria; comparación con el período anterior; exportar a CSV y PDF; el encargado no ve el resultado económico.

**Architecture:** Los reportes se calculan **en el servidor** con consultas SQL sobre cobros, pagos, movimientos, pedidos e ítems (spec §8: sin tablas de agregados). La PC solo guarda la operación del día (24 h), así que **los reportes necesitan conexión**: la PC los pide con `GET /reportes?desde=&hasta=` y los muestra; sin red dice "Los reportes necesitan conexión". El día se cuenta como **día operativo** (Buenos Aires, la noche hasta las 06:00 es del día anterior), igual que la numeración de pedidos. Los períodos y su "anterior" son funciones puras en `@gula/shared`; el CSV y el HTML del PDF son funciones puras en la PC; el PDF lo genera Electron (`printToPDF`) en main.

**Tech Stack:** el de las fases 1–7. Sin dependencias nuevas.

**Spec:** `docs/superpowers/specs/2026-11-18-gulaweb-design.md` (§8 último párrafo, §9 Reportes, §10 fila Reportes). Base: fases 1–7.

## Global Constraints

- Todas las de las fases 1–7. Montos en centavos.
- Rango: `desde` y `hasta` son días operativos `AAAA-MM-DD`, ambos incluidos; como máximo 366 días; `desde ≤ hasta`.
- Semana: lunes a domingo. Mes, trimestre (ene–mar…), semestre (ene–jun / jul–dic) y año: calendario. Período anterior: la unidad calendario anterior (el mes anterior, etc.); para personalizado, los mismos días inmediatamente antes.
- Una venta cuenta en el día operativo en que **se cobró** (`cobros.cobrado_en`). Ventas = Σ `cobros.total` (con descuento, con envío). Propinas aparte (no son venta). Egresos e ingresos = movimientos de caja por `hecho_en`.
- Resultado = ventas − egresos. **Solo con `reportes.resultado`** (dueño): para el encargado la respuesta no trae `egresos`, `ingresos` ni `resultado` (no se oculta en la pantalla: no viaja).
- Origen: `salon` (cobro de mesa), `mostrador`, `delivery`.
- Productos y meseros se miden sobre los ítems vigentes de los pedidos cobrados en el período, a precio de lista (antes de descuentos); el mesero es quien tomó el pedido (`creado_por`, o `confirmado_por` en los QR).
- CSV: separador `;`, coma decimal, UTF-8 con BOM (lo abre bien el Excel en español).
- Permiso `reportes.ver` (encargado, dueño).

## Review Focus

1. **Cobros de madrugada** (01:30 del sábado) → cuentan para el viernes, igual que el número de pedido; un rango de un solo día los incluye. → test en Task 2.
2. **Encargado pidiendo el reporte** → la respuesta (y por lo tanto el CSV/PDF) no trae egresos ni resultado. → tests en Task 2 y Task 5.
3. **Período sin ventas** (o anterior sin ventas) → todo en 0, ticket promedio 0, variación "—" en vez de dividir por cero o mostrar NaN/Infinity. → tests en Task 1 y Task 5.
4. **Mesa cobrada en dos veces** (un pedido quedó sin cobrar y se cobró después, misma sesión) → cada pedido se cuenta una sola vez en productos y meseros. → test en Task 2.
5. **Sin conexión o rango inválido** (hasta antes que desde, más de un año) → mensaje claro, sin pantalla rota. → tests en Task 2 y Task 5.

### Task 2: Reporte en la API

**Files:** Create `apps/api/src/reportes/consultas.ts`, `apps/api/src/reportes/rutas.ts` · Modify `src/app.ts` · Test: `test/reportes.test.ts`

**Interfaces — Produces:**
- `GET /reportes?desde=&hasta=` (`reportes.ver`) → `{ actual: Reporte; anterior: Reporte; rango: Rango; rangoAnterior: Rango }`; el anterior se calcula con `periodoAnterior('personalizado', …)` salvo que venga `tipo` en la query (`?tipo=mes`), que usa el anterior calendario. Rango inválido → 400 `DATOS_INVALIDOS`.
- `type Reporte` (en `@gula/shared`, exportado desde `reportes.ts`):
  ```ts
  {
    ventas: number; cobros: number; ticketPromedio: number; propinas: number; descuentos: number; envios: number;
    porMetodo: { metodo: MetodoPago; monto: number; propinas: number }[];
    porOrigen: { origen: 'salon' | 'mostrador' | 'delivery'; ventas: number; cobros: number }[];
    porHora: { hora: number; ventas: number; cobros: number }[];          // 0–23, solo las que tienen algo
    productos: { productoId: string; nombre: string; cantidad: number; importe: number }[]; // top 20 por cantidad
    meseros: { usuarioId: string | null; nombre: string; pedidos: number; importe: number }[];
    egresos?: number; ingresos?: number; resultado?: number;            // solo con reportes.resultado
  }
  ```
- `leerReporte(tx, rango, conResultado: boolean): Promise<Reporte>` — el día operativo en SQL: `((t AT TIME ZONE 'America/Argentina/Buenos_Aires') - interval '6 hours')::date`.

- [ ] **Step 1: Tests que fallan** (datos insertados directo con fechas fijas) — dos cobros (efectivo 10.000 + propina 1.000; débito 5.000 con descuento 500) el 2026-11-18: ventas 15.000, ticket 7.500, propinas 1.000, por método correcto; un cobro a las 01:30 del 19 (hora BA) cuenta en el 18; un egreso de 2.000 → resultado 13.000 para el dueño y sin `resultado`/`egresos` para el encargado; mesero → 403; delivery con envío 1.500 cuenta en origen `delivery` y en `envios`; una mesa cobrada en dos cobros cuenta cada pedido una vez en productos; productos ordenados por cantidad; meseros con nombre; `anterior` del rango 18..18 es el 17; `hasta < desde` → 400; otro local no suma.
- [ ] **Step 2–5** — commit `feat(api): reportes`
