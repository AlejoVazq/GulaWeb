# Fase 7 — Delivery: Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Pedidos de delivery cargados a mano en la PC (llamada/WhatsApp) con cliente, dirección, costo de envío y "paga con"; comanda por sector más un ticket para el repartidor; tablero propio con estados preparando → en camino → entregado; cobro al entregar (o antes, si pagó por transferencia); todo funcionando sin internet.

**Architecture:** Un delivery es un **pedido** con `origen = 'delivery'` (sin mesa) más una fila 1:1 en una tabla `deliveries` (id = id del pedido) con los datos del cliente y el estado de reparto. Viaja en el pull del salón (`/sync/salon` suma `deliveries`), así no hay cursor nuevo. Dos operaciones de outbox nuevas: `delivery.crear` (crea pedido + ítems + delivery, nace `confirmado`) y `delivery.estado` (avanza el reparto). El cobro reutiliza `cuenta.cobrar` con `pedidoId` (subtotal = ítems + envío); la cancelación reutiliza `pedido.anular` (con PIN si es mesero).

**Tech Stack:** el de las fases 1–6. Sin dependencias nuevas.

**Spec:** `docs/superpowers/specs/2026-11-18-gulaweb-design.md` (§8 Pedido/Delivery, §9 Delivery, §10 fila Delivery, §12 comanda). Base: fases 1–6.

## Global Constraints

- Todas las de las fases 1–6. Montos en centavos enteros; envío y "paga con" ≤ `MONTO_MAXIMO_CAJA`.
- Estados de reparto: `preparando` → `en_camino` → `entregado`; solo avanzan (se puede saltar de `preparando` a `entregado`). La cancelación es el pedido `anulado`, no un estado de reparto.
- **No se marca `entregado` sin cobrar** (`CUENTA_PENDIENTE`): la PC ofrece "Cobrar y entregar".
- Permiso `delivery.gestionar` (todos los roles) para crear y mover estados; cobrar sigue pidiendo `cobro.registrar`; anular, `pedido.anular` (mesero con PIN de encargado).
- Cliente: nombre 1–80, teléfono 0–30, dirección 1–200, referencias 0–140; repartidor 0–60. Texto pasado por `sinControl` (llega a la impresora).
- Total de un delivery = ítems vigentes + envío. El envío por defecto se guarda en la PC (`kv`), lo edita quien tiene `admin.configurar`, y se puede cambiar en cada pedido.
- Estética mínima funcional (fase 10).

## Review Focus

1. **Se corta internet con deliveries en curso** → se cargan, salen, se cobran y se entregan igual; al volver, el servidor queda con el mismo estado y el cobro una sola vez. → test en Task 6 (integración).
2. **Marcar entregado sin cobrar** (o que la operación de entrega llegue al servidor antes que el cobro) → la PC no deja y el servidor responde `CUENTA_PENDIENTE`; "Cobrar y entregar" encola el cobro antes que la entrega. → tests en Task 2 y Task 6.
3. **Estado que retrocede o se repite** (doble clic en "Salió", o `en_camino` después de `entregado`) → la PC lo ignora/rechaza y el servidor responde `ESTADO_INVALIDO` sin tocar la fila. → tests en Task 2 y Task 6.
4. **Delivery cancelado** (anulado con PIN) → sale del tablero activo, va a "Cancelados", imprime "ANULADO" a cocina y no se puede cobrar ni entregar. → tests en Task 5, Task 6 y Task 7.
5. **"Paga con" menor que el total o datos del cliente con caracteres de control** → la PC lo rechaza con mensaje claro; el ticket nunca imprime control crudo. → tests en Task 6 y Task 5.

### Task 2: Delivery en la API (esquema, operaciones, pull)

**Files:** Modify `apps/api/src/db/schema/salon.ts` (origen `delivery` en enum y check; tabla `deliveries`), `src/salon/operaciones.ts` (extraer `insertarPedido`), `src/salon/pull.ts`, `src/sync/rutas.ts` (importar operaciones) · Create migraciones `0012_delivery.sql` (generada con `pnpm --filter @gula/api db:generar`) y `0013_delivery_rls.sql` (RLS + trigger + grants, como `0010`), `src/delivery/operaciones.ts` · Test: `test/delivery.test.ts`

**Interfaces — Produces:**
- `deliveries(id = pedido_id, pedido_id unique FK, cliente_nombre, telefono, direccion, referencias, costo_envio bigint ≥ 0, paga_con bigint null, repartidor null, estado check, en_camino_en null, entregado_en null)` + `sincronizable()`.
- `insertarPedido(tx, sesion, hechaEn, d: { pedidoId; origen; sesionId|null; mesaId|null; numero; dia; notas; items })` — lo usan `pedido.crear` y `delivery.crear`.
- `delivery.crear` (`delivery.gestionar`, tema `salon`) `{ pedidoId, numero, dia, notas?, items (como pedido.crear), cliente: { nombre, telefono, direccion, referencias }, costoEnvio, pagaCon? }` → pedido `confirmado` origen `delivery` + fila `deliveries` en `preparando`.
- `delivery.estado` (`delivery.gestionar`, tema `salon`) `{ pedidoId, estado: 'en_camino' | 'entregado', repartidor? }` — pedido anulado → `ESTADO_INVALIDO`; `!avanzaReparto` → `ESTADO_INVALIDO`; `entregado` con pedido no `cobrado` → `CUENTA_PENDIENTE` (409); guarda `en_camino_en`/`entregado_en` (con `hechaEn`) y el repartidor si viene.
- `/sync/salon` devuelve `deliveries` (completo: los de los pedidos que trae; `desde`: cambiados).

- [ ] **Step 1: Tests que fallan** — crear un delivery con envío 150.000 deja pedido `delivery`/`confirmado` y delivery `preparando`; cobrarlo con `cuenta.cobrar` `{ pedidoId, subtotal: ítems + envío }` y después `entregado` → `entregado_en` guardado; `entregado` sin cobrar → `CUENTA_PENDIENTE`; `en_camino` tras `entregado` → `ESTADO_INVALIDO`; estado sobre pedido anulado → `ESTADO_INVALIDO`; mesero puede crear; el pull completo y el incremental traen la fila; RLS: otro local no la ve.
